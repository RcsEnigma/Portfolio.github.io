# Portfolio

Drop files in a folder, run one command (or double-click one file), push to GitHub. Done.

---

## File structure

```
/
├── index.html              — main gallery page (grid, carousel, popup, zoom overlay, shareable links)
├── page-engine.js          — renders subpages from pages.json (widgets + their own zoom overlay)
├── generate-manifest.js    — the build script; run this after adding/changing files
├── update-site.bat         — Windows: double-click to run the build script (see "Running the build")
├── theme.css               — shared color variables, used by subpage stubs
├── page-widgets.css        — subpage widget layout styles
├── 404.html                — "not found" page; also sends dead /w/... share links to the homepage
├── robots.txt              — keeps search engines out, lets link-preview bots in (see "Staying unlisted")
├── package.json            — lists the one npm dependency (sharp)
├── README.md               — this file
├── manifest.json           — generated: gallery data, gated works excluded (don't hand-edit)
├── manifest-full.json      — generated: gallery data, everything included (don't hand-edit)
├── pages.json              — generated: subpage data (don't hand-edit)
│
├── works/                  — drop gallery images/videos + their .txt files here
│   └── thumbs/              — generated: thumbnails, zoom-tier images, video posters, web-safe video copies
│
├── pages/                  — one subfolder per subpage
│   └── <page-name>/
│       ├── _page.txt         — page-level settings (label, order, featured, carousel)
│       ├── 01_widget.txt     — numbered widget files, one per section
│       ├── your-media.jpg
│       └── thumbs/           — generated: same kinds of files, for this page
│
├── w/                      — generated: one tiny page per work (and per attached item) for shareable links
│   └── <name>.html          (see "Shareable links and previews")
│
├── full/                   — generated: exact copy of index.html, loads manifest-full.json
│   ├── index.html            (see "Hiding mature/violent works by default")
│   └── w/                    — generated: share-link pages + blurred preview images for gated works
│
└── works-src/              — optional, local only (git-ignored): untouched originals of files the script
                              had to shrink to fit GitHub's size limit (see "Files over 100 MB")

/<page-name>/                — generated stub at the repo root for each subpage,
    └── index.html             giving it a clean URL like yoursite.com/page-name/
```

Everything under `thumbs/`, `w/`, `full/`, and the root-level subpage stub folders is generated by `generate-manifest.js` — don't edit those by hand, they get overwritten and cleaned up automatically on the next run.

## Setup (do this once)

1. Put everything in a folder and push it to a GitHub repo
2. In your repo settings, enable GitHub Pages (Settings > Pages > Deploy from main branch). If you use a custom domain, set it there too.
3. Install Node.js from nodejs.org if you don't have it
4. Open a terminal in your portfolio folder and run `npm install` (installs `sharp`, the image compression tool). `update-site.bat` does this for you the first time it runs.
5. Install ffmpeg (needed for videos — see below). **Without ffmpeg the script still runs, but videos get no poster images and no web-safe copies.** On Windows: `winget install Gyan.FFmpeg`, then close and reopen your terminal. On Mac: `brew install ffmpeg`. On Linux: `sudo apt install ffmpeg`. Check with `ffmpeg -version` and `ffprobe -version` — both should print a version number.
6. Make sure `.gitignore` contains `node_modules/` (so that folder doesn't get committed) and `works-src/` (the script adds this one itself the first time it needs it)
7. Open `generate-manifest.js` and set `SITE_URL` (your site's address, no trailing slash — currently `https://ajambrozic.com`) and `SITE_NAME` near the top. These are used to build link previews.

## Running the build

Any time you add or change files, rebuild:

- **Windows, easiest:** double-click `update-site.bat`. It checks that Node and ffmpeg are installed, runs `npm install` the first time, runs the build, and keeps the window open so you can read the output.
- **Anywhere:** open a terminal in the folder and run `node generate-manifest.js`.

When it starts it prints which version of the script you're running and which ffmpeg it found. Read the end of the output: it lists any video that couldn't get a poster or web copy (and why), any file still too big for GitHub, and a boxed warning if ffmpeg is missing. If you close the window before it says "Done compressing", the run was interrupted — just run it again.

## Adding a new work

1. Drop your image/video file into `/works/`
2. Drop a `.txt` file with the same name into `/works/`
3. Run the build (double-click `update-site.bat`)
4. Commit and push with GitHub Desktop

That's the whole loop every time.

## The .txt file

Every field is optional. You can use any combination.

```
[title]
My Work Title

[description]
Whatever you want to write here.
URLs like https://yoursite.com/page automatically become clickable links.

[tags]
3D, animation, sci-fi

[date]
2024-11

[featured]
true

[square]
true

[link]
https://vimeo.com/whatever

[extra]
mywork_02.jpg, mywork_03.mp4
```

**What each field does:**

`[title]` - shows on hover, in the popup, and as the title of link previews. defaults to filename if you leave it out.

`[description]` - shows in the popup info panel. The first ~200 characters also appear in link previews.

`[tags]` - comma separated. they show up as filter buttons on the site. selecting multiple tags filters to works that have ALL of them (not any of them).

`[date]` - any string. works sort newest first by this field.

`[featured]` - set to true and it shows up in the big carousel at the top of the page.

`[square]` - set to true to force a 1x1 square grid cell regardless of the image's actual dimensions.

`[link]` - shows as a clickable link in the popup.

`[extra]` - list extra files to bundle into this same gallery entry (comma separated filenames).

---

## Grouping multiple files together

Two ways to do this:

**Numbered filenames** - name your files `project_01.jpg`, `project_02.jpg`, `project_03.mp4` with the same base name. They'll automatically bundle together. The lowest numbered one becomes the thumbnail.

**The [extra] field** - list additional filenames directly in the txt file. Useful when the files have different names.

## Grid sizes

The grid automatically picks a span based on the image's real dimensions. Landscape goes wide, portrait goes tall, square stays square. Videos default to wide.

You can override it with `[square]\ntrue` in the txt file to force a 1x1 cell.

**Video tiles.** A tile whose first file is a video shows a small white play triangle in its bottom-right corner. On desktop, hovering the tile plays a muted preview and the triangle fades out while it plays. On phones and tablets (no hover) video tiles are static poster images and nothing is downloaded until you open the work. A work whose first file is an image but which has videos attached further in gets no triangle.

---

## The carousel

The big carousel at the top shows any work with `[featured]\ntrue` in its txt file. It also shows any subpages (see below) that have `[featured]\ntrue` in their `_page.txt`. Clicking a work slide opens its popup. Clicking a subpage slide takes you to that page.

Video slides autoplay muted. If the browser refuses (iOS Low Power Mode, data saver) or can't play the format, the slide just keeps showing its poster image; tapping it opens the work as usual. Only the visible slide plays. Auto-advance pauses while a popup is open and resumes from the same slide when it closes.

## Using the gallery (controls)

**Popup (a work opened from the grid)**

| | Desktop | Phone / tablet |
|---|---|---|
| Next/previous attached file | ← / → keys, on-image arrows, dots | swipe left/right on the image |
| Next/previous **work** (follows the active tag filters; "previous" = newer, "next" = older; wraps around) | ↑ / ↓ keys, or the tall arrow buttons at the left/right edge of the screen | swipe left/right on the description, or the small ‹ › buttons in the top bar |
| Close | Esc, X, or click outside | X, or swipe **down** on the image |
| Zoom (images only) | Zoom button, or click the image | Zoom button, or tap the image |
| Copy a link to this exact item | Link button | Link button |

Vertical swipes on the description still just scroll the text. To make post navigation stop at the first/last work instead of wrapping, set `POST_NAV_WRAP = false` near the top of the post-navigation code in `index.html`.

**Zoom view** — scroll / pinch to zoom, drag to pan. If the work has more than one attached file, round arrows at the left/right edges (and the ← / → keys) step through them, wrapping from last to first; on a phone you can also swipe, but only when the image is fully zoomed out (otherwise a one-finger drag pans). Stepping onto a video shows it full-screen with controls. Esc or X closes; when you close, the popup behind it is on the item you were last looking at. The Link button copies a link straight to the zoomed image.

**Subpage zoom** works the same way, except each widget is its own set: arrows step only through the images/videos in the widget you clicked, never into another widget. In a carousel widget the strip underneath follows along, and its autoplay is paused while zoom is open.

## Shareable links and previews

Every state of the gallery has a clean, shareable URL, and the address bar always shows it:

| What you're looking at | URL |
|---|---|
| Grid with filters | `yoursite.com/?tag=3D&tag=art` |
| A work | `yoursite.com/w/neon-drift` |
| Its 3rd attached item | `yoursite.com/w/neon-drift--3` |
| ...in the zoom view (link straight to the 4K image) | `yoursite.com/w/neon-drift--3?zoom=1` |
| A gated work | `yoursite.com/full/w/<name>` |

Use the **Link** button in the popup or zoom view to copy the current one. Filters never create history entries; opening a popup and opening zoom each do, so the browser's Back button steps zoom → popup → grid, and **Forward** steps back in (it re-opens the popup, then the zoom view). Older-style links like `/?work=neon-drift&m=3&zoom=1` still work. A link to a work that doesn't exist (renamed, removed, or a gated work on the public site) just shows the grid.

**How the previews work.** GitHub Pages is a static host — there's no server to write per-link `<meta>` tags — and link-preview bots (Discord, Slack, iMessage, Facebook, X...) don't run JavaScript. So the build writes one tiny HTML file per work *and per attached item* into `w/`: `w/neon-drift.html` (served at `/w/neon-drift`), `w/neon-drift--2.html`, and so on. Each holds that item's title, description excerpt and image as Open Graph/Twitter tags, then forwards real visitors into the gallery with that item open. They're generated, `noindex`, and cleaned up automatically when a work disappears — never edit them.

- **Title** = the work's `[title]`; **description** = the first ~200 characters of `[description]` (or its tags if there is none).
- **Image** = that item's existing WebP thumbnail (or video poster) — no extra image files are made for public works.
- **Video works** also get an inline-playable `og:video` (Discord) but only when the playable MP4 is under 20 MB and conservative (H.264, yuv420p, AAC-LC audio or none). Turn it off entirely with `OG_VIDEO_ENABLED = false` in `generate-manifest.js` — previews then show the poster image only.
- **Slugs** come from the filename: lowercased, accents folded, anything else becomes `-` ("Café & More" → `cafe-more`). Renaming a file changes its link. Old links don't break badly: an unknown `/w/name` or `/w/name--7` falls back (via `404.html`) to the work itself or the homepage.
- Reserved folder names for subpages: `full` and `w`.

**Gated works** (see next section) get their pages under `full/w/`, so the `/full` in the link is the gate. Their link preview shows the real title and description but a heavily **blurred** copy of the image (saved as `full/w/<name>.preview.webp`); the real image only appears after clicking through, and gated videos get the blurred still with no inline video. A link preview can't offer a click-to-reveal, so blur is the substitute. If `sharp` isn't installed, gated previews get no image at all — never the unblurred one.

**Settings** (top of `generate-manifest.js`): `SITE_URL`, `SITE_NAME`, `OG_DESC_MAX` (excerpt length), `OG_VIDEO_ENABLED`, `OG_VIDEO_MAX_BYTES`, `OG_BLUR_WIDTH` / `OG_BLUR_SIGMA` (blur strength for gated previews).

**Testing / caching.** After pushing, paste a work's `/w/...` link into Discord, Slack and iMessage. Chat apps cache previews, so after changing a work's title/description/image an app may keep showing the old one for a while (and Facebook/X have debugger tools to re-fetch). Previews show the item's own image, not a crop of whatever part you were zoomed into.

## Staying unlisted (search engines)

The site is meant to be reachable by link but not appear in Google. `robots.txt` blocks all crawlers (`User-agent: *` / `Disallow: /`) and then names the link-preview bots (Discordbot, Twitterbot, facebookexternalhit, Slackbot, LinkedInBot, WhatsApp, TelegramBot) with `Allow: /` so their previews still work. Every page the script generates, plus `index.html`, also carries a `noindex, nofollow` meta tag. If a preview bot you care about isn't showing previews, check whether it needs adding to `robots.txt` (and note that iMessage's behaviour isn't covered by any list). This reduces discoverability but isn't a guarantee: your GitHub repo is public and separately indexable, other sites linking to you can surface the URL, and `noindex` tags can't apply to image files themselves on GitHub Pages.

## Hiding mature/violent works by default (`/full/`)

Tag a work `[tags]\nviolent` or `[tags]\nmature` (comma-separated alongside any other tags, case doesn't matter) and it's left out of the main site entirely — not hidden with CSS, not filterable-but-present, genuinely absent from the data the main site ever loads. It only shows up at **`yoursite.com/full/`**, which is otherwise identical to your homepage (same grid, same carousel, same popup, same everything) but includes those works too.

How it works under the hood: `generate-manifest.js` builds two data files — `manifest.json` (everything except gated works, what the homepage loads) and `manifest-full.json` (everything, what `/full/` loads). `/full/index.html` is an exact copy of your root `index.html`, refreshed automatically every time you run the script — you never edit it directly, and there's nothing to keep in sync by hand. Gated works also get share-link pages under `full/w/` (see above).

**This is a default-visibility gate, not real access control.** `/full/` has no password, and the image files themselves are just as publicly fetchable on GitHub Pages as anything else on the site to anyone who has (or guesses) the direct URL. The share-link pages and blurred previews are likewise just public files. It's meant to spare casual visitors from content they didn't ask to see by default, not to keep it truly private. There's also no link to `/full/` from the main site anywhere — it's discoverable only if you share the URL yourself.

The gated tag list lives in `generate-manifest.js` as `GATED_TAGS` (currently `["violent", "mature"]`) if you want to rename it or gate more tags. This only applies to the main `works/` gallery, not subpages. Also: don't name a subpage folder `full` or `w` — those names are reserved, and the script will skip the folder with a warning if it collides.

## Thumbnails and image compression (speeds up loading, prevents crashes)

After `npm install`, the script automatically generates compressed images in a `thumbs/` folder next to your source files (`works/thumbs/` for the main gallery, `pages/<page-name>/thumbs/` for subpages). There are two tiers:

**Display tier** — `<n>.webp`, capped at 1200px on the long side, WebP quality 82. Used by the grid, carousel, and the popup, for every file in a multi-file gallery entry (not just the first one).

**Zoom tier** — `<n>_zoom.webp`, capped at 4096px on the long side, WebP quality 90. This is what the pan/zoom overlay opens on phones and tablets when you tap to zoom in.

Why zoom needs its own tier, and why it's capped rather than just compressed: the zoom overlay renders its image inside a layer that the browser promotes to the GPU for smooth panning. That means the browser has to allocate a texture sized to the image's **decoded pixel dimensions** — not its file size. A photo can be a small file and still have enormous pixel dimensions (or vice versa), and either way, a big enough one can exceed an older phone's texture/memory limit and crash the tab, even though it's only ever shown scaled down on screen. Re-encoding to WebP shrinks bytes on disk and speeds up the download, but it does nothing about that decode-time memory footprint — only capping the actual pixel dimensions does. 4096px is comfortably past what any screen can show pixel-for-pixel even at max pinch-zoom on a phone, so this shouldn't look like a quality loss there. If you want more true full-resolution headroom, raise `ZOOM_MAX_PX` at the top of `generate-manifest.js` (at the cost of reintroducing crash risk on old phones).

The zoom tier is generated for **every** image, including subpage widget images, regardless of that widget's `[compress]` setting — `[compress]` only controls the display-tier thumbnail, since the zoom-tier cap is a stability safeguard rather than a look/quality choice.

If sharp isn't installed, or a zoom-tier image fails to generate for some reason, the zoom overlay falls back to the raw original file — so it still works, just without the size cap.

GIFs are skipped for both tiers (compressing them kills the animation) — they always load as their original file.

**Desktop/laptop gets the true original.** On a device with a mouse (not a touchscreen) and a reasonably wide window, the zoom overlay loads the actual full-resolution original instead of the capped zoom tier — desktops and laptops have far more memory headroom than phones, so there's no need to cap them, and you get genuinely full detail. There's no reliable way for a webpage to read real hardware specs (Safari in particular exposes almost nothing along those lines), so this is a heuristic — "mouse as the primary pointer + window at least 900px wide" — not an actual benchmark. If it ever misclassifies a device you care about, adjust `DESKTOP_MIN_WIDTH` near the top of the pan/zoom code in `index.html` (and the matching `PZ_DESKTOP_MIN_WIDTH` in `page-engine.js`).

**Caching.** Regeneration is skipped if an output already exists and the source file's byte size hasn't changed since it was made — tracked in a small `.thumb-cache.json` file inside each `thumbs/` folder. This is deliberately based on file size, not modification time: git doesn't preserve mtimes across commits/pulls/clones, so an mtime-based freshness check can come out wrong essentially at random after any git operation. Size is stable across all of that, and only changes when you genuinely replace a source file. `.thumb-cache.json` is meant to be committed along with the thumbnails it describes — don't gitignore it or hand-edit it. Failed items aren't cached, so they're retried on the next run. If you ever want to force a full clean rebuild (e.g. to rule out a caching issue while troubleshooting), just delete the relevant `thumbs/` folder entirely and re-run the script.

**Progress.** Compressing a full library of large photos/videos can take a while — the script prints a live progress bar and an explicit "do not close this window" notice while it works, and a "Done compressing" line once it's finished.

## Videos (ffmpeg)

Videos need ffmpeg (and its companion `ffprobe`) installed — see Setup. For each video the script does two separate things:

**Poster image** — `<name>_poster.webp`, in `thumbs/`. Instead of blindly taking frame 0 (often black: fade-ins, title cards), it samples several candidate frames (around 0s, 0.5s, 1s, 2s, 3s, 5s and a few points through the video) and uses the first one that's bright and contrasty enough; if none is, the best-scoring one wins. (Tune with `POSTER_MIN_LUMA` / `POSTER_MIN_STDEV`.) The poster is what grid tiles show on phones, what the popup shows while a video loads, what the hero shows when it can't autoplay, and what link previews use. Without `sharp`, a plain JPEG at about one second is made instead.

**Web-safe copy** — `<name>_web.mp4`, in `thumbs/`. Some files can't play everywhere (iOS Safari can't play `.mkv` at all, whatever's inside it). A copy is made **only when needed** — when the file isn't an `.mp4`, isn't H.264 / `yuv420p` pixel format / AAC-or-MP3 audio, is larger than 1080p-class (long side over 1920px), or has its metadata at the *end* of the file (which makes iOS download most of the file before it can start — the usual cause of a long gray loading screen). If metadata placement is the only problem, the streams are copied untouched (lossless, fast); otherwise it's re-encoded to H.264/AAC at CRF 23, long side capped at 1920. The site automatically plays the copy instead of the original wherever one exists; files that are already fine get no copy, so repo size doesn't double. Tune with `VIDEO_WEB_MAX_LONG_SIDE` and `VIDEO_WEB_CRF`. Web copies are made for subpage videos too (regardless of `[compress]`).

**When something goes wrong** the script says so in plain words — `poster FAILED` / `web copy FAILED` lines as it goes, and a "Videos with problems" list at the end with a hint (for example, "this ffmpeg can't decode the video's codec — update ffmpeg"). Failed videos are retried next run. A work with no poster is labelled `[NO VIDEO POSTER: ...]` in the output. If ffmpeg isn't found at all you get a boxed warning at the *end* of the run.

If a video still can't play in a browser (e.g. an `.mkv` with no web copy on iOS), the popup shows a "can't be played in this browser" message with an **Open the file** link instead of a blank gray box, and grid/hero tiles keep showing the poster.

## Files over 100 MB

GitHub rejects any pushed file over 100 MB. At the start of every run the script finds media files over 95 MB (`SIZE_LIMIT_BYTES`) in `works/` and each `pages/<page-name>/` folder and shrinks them automatically:

1. The untouched original is copied to `works-src/` (same relative path), and `works-src/` is added to `.gitignore`. **That copy exists only on your computer — keep your own backup too.**
2. A smaller version is made: videos become H.264 `.mp4` (CRF 23 first; if that's still too big, a bitrate calculated from the duration, retrying lower and finally at a lower resolution); big PNG/WebP/AVIF become high-quality `.webp`; big JPEGs are re-encoded. GIFs and SVGs can't be shrunk automatically.
3. Only once the result is verified to be under the limit does it replace the original. If it can't get under the limit, your original is left exactly as it was and you get a warning.

If the extension changes (e.g. `.mkv` → `.mp4`), any `[extra]` / `[media]` / `[carousel_media]` lines in the neighbouring `.txt` files that named the old file are updated for you. At the end of every run, any file anywhere in the repo that's still over the limit (including non-media like game builds) is listed.

## Subpages

You can make custom project pages that live at `yoursite.com/pagename/`.

Create a folder inside `/pages/` with the page name. Inside it, put:
- `_page.txt` for page-level settings
- Numbered `.txt` files for each section/widget on the page
- Your media files for that page

Run the build and the page stub gets created automatically. Delete the source folder and run again and the stub gets cleaned up automatically.

### _page.txt

```
[label]
Studies

[order]
1

[featured]
true

[carousel_media]
hero.jpg

[carousel_caption]
A short description for the homepage carousel slide.
```

`[label]` - the name shown in the nav and at the top of the page.
`[order]` - controls left-to-right order in the nav (lower number = further left).
`[featured]` - shows this page in the homepage carousel.
`[carousel_media]` - which file to use as the carousel slide image or video (must be in the same page folder). if you skip this it uses the first image it finds in your widgets.
`[carousel_caption]` - text shown under the title in the carousel slide.

### Widget files

Name them `01_whatever.txt`, `02_whatever.txt` etc. The number controls the order they appear on the page.

```
[type]
image-left

[title]
Section Title

[text]
Body text goes here.

[media]
myimage.jpg

[background]
#1a1a1a

[compress]
false
```

`[type]` - picks the layout (see below).
`[title]` - section heading.
`[text]` - body copy.
`[media]` - file(s) to use. some types need more than one.
`[background]` - hex color for the section background. if it's a light color the text automatically switches to dark so it stays readable.
`[compress]` - set to false to skip display-tier thumbnail/poster generation for this widget's media. defaults to true. (Zoom-tier images and web-safe video copies are always made — see above.)
`[game]` - only for `game-embed`: see below.

### Layout types

`image-left` - image on left, text on right. on mobile stacks image above text.

`text-left` - text on left, image on right. on mobile stacks image above text.

`split` - text in the middle, one image on each side. needs two files in [media]. on mobile stacks them vertically.

`media-only` - single centered image or video with playback controls.

`full-bleed` - edge to edge media with a big title overlaid in the center.

`text-only` - centered text block, no image.

`carousel` - film strip carousel. center item is large and uncropped, neighbors peek in from the sides. 5 to 7 images works best. on mobile shows 3. Auto-advances every 5 seconds (paused while zoom is open).

`trio` - three images side by side in equal columns, no text. needs three files in [media]. on mobile stacks them.

`title-bar` - big centered heading, good for dividing sections.

`game-embed` - a click-to-play embedded Unity WebGL game. Put the game's build (its own `index.html` plus `Build/` output) in a subfolder of the page folder — `game/` by default, or set `[game]` to another subfolder name. `[media]` is optional and, if given, is the poster image shown before play. Builds must be **uncompressed** (not Brotli/Gzip-precompressed): GitHub Pages doesn't send the headers those need. Large build files still count toward the 100 MB limit — the script warns about them but can't shrink them. On Android the page's scroll-snapping around the embed is switched off (it fought with the game's touch handling).

### Images and videos are zoomable on subpages

Clicking any image in a widget opens the same full pan/zoom view as the main gallery, with arrows / ← → / swipe to step through that widget's media (see "Using the gallery"). Scroll to zoom, drag to pan, Esc or the X button to close.

## Troubleshooting

**Videos have no poster / `[no thumb]` or `[NO VIDEO POSTER ...]` next to a video.** Almost always ffmpeg: run `ffmpeg -version` and `ffprobe -version` in the same terminal you build from. "Not recognized" means it isn't installed or isn't on your PATH (install it fresh; after installing, open a *new* terminal window). If both print versions, read the "Videos with problems" list at the end of the build output.

**An `.mkv` says "not supported" on iPhone.** iOS can't play the Matroska container. It needs a web-safe copy, which needs ffmpeg — see above. Re-run the build and push the new `_web.mp4` files in `thumbs/`.

**Grid video tiles are blank on iPhone.** No poster was generated (see the first item) — iOS doesn't paint a video's first frame by itself.

**A shared video embeds in Discord but won't play when clicked** (thumbnail and duration show, the time never moves). Discord's desktop app has a long history of this exact symptom, including with videos people upload to Discord directly, so first check whether the same embed plays in Discord in a web browser or on a phone. If it does, it's Discord's client, not the site. If it fails everywhere, check that `https://yoursite.com/works/thumbs/<name>_web.mp4` (or the original MP4) opens and plays on its own, that your domain doesn't redirect between `www` and the bare domain, and that its audio is AAC-LC (HE-AAC is reported to be a problem in some Discord clients). As a fallback set `OG_VIDEO_ENABLED = false` so previews show the poster image only.

**A link preview shows the wrong/old image or text.** The chat app cached it. Wait, or use the platform's link debugger / paste the link with a throwaway `?x=1` on the end.

**The build says a work was skipped / a subpage folder was skipped.** Folder names `full` and `w` are reserved.

## Notes on fixes and known behavior

**Zoom-overlay crash on older phones (fixed, confirmed on an iPhone 7).** The zoom overlay renders its image inside a layer the browser promotes to the GPU for smooth panning, which means the browser has to allocate a texture sized to the image's *decoded pixel dimensions* — regardless of file size, and regardless of what scale it's displayed at. A big enough original can exceed an older phone's texture/compositor limit and crash the tab. Fixed by generating a size-capped "zoom tier" image so the overlay never hands the browser an unbounded image in the first place. A smaller bug was fixed alongside it: the gallery zoom overlay wasn't resetting its on-screen pan/zoom transform when opening a new image.

**Thumbnail caching used to key off file modification time (fixed).** `git` does not preserve mtimes, so an "is this thumbnail newer than its source?" check came out true or false almost arbitrarily after any git operation. Now keyed on file byte size in `.thumb-cache.json`.

**Multi-file gallery entries loading full-res images into the popup (fixed).** Thumbnails are now generated for every file in an entry, not just the first.

**Subpage zoom didn't disable native pinch-zoom (fixed).** Added for parity with the gallery zoom, so iOS hands two-finger gestures to the custom pan/zoom handler.

**Videos on iOS (fixed).** Video tiles showed blank in the grid and videos in the popup sat on a gray loading screen: no poster was ever generated, nothing told iOS to preload, the loading spinner was dismissed immediately, and `.mkv` can't be played at all. Now: posters are generated, videos use web-safe copies, grid tiles are static posters on touch devices, the popup shows the poster plus a spinner until data arrives, and a failed load shows a message with an "Open the file" link.

**Carousels kept advancing behind zoom/popup (fixed).** The subpage carousel and the homepage hero ignored open overlays, so closing zoom left you on a different slide. Both now pause while an overlay is open, and zoom stepping moves the subpage strip along with you.

**Android scroll-snap (fixed).** The `game-embed` widget's scroll-snap fought Chrome on Android; it's now switched off there. (Chrome's "Request desktop site" mode hides "Android" from the browser, so snapping returns in that mode.)

**Back/Forward model.** Opening a popup and opening zoom each add one history entry (grid → popup → zoom); Back and Forward step through them and the address bar always matches. Switching works or attached items, and filtering, replace the current entry instead of adding one.

**Subpage zoom doesn't blank other on-screen thumbnails.** The gallery zoom overlay clears every other visible thumbnail right before loading the zoom image, freeing memory headroom for the decode. The subpage zoom overlay doesn't. This mattered a lot more before the zoom-tier size cap existed; it's worth porting if subpages ever show signs of the same memory pressure.

**Known limits.**
- A link to slide N previews slide N's own image, but not whichever *part* of it you zoomed into.
- Chat apps cache previews; changes can take a while to show.
- `works-src/` originals live only on your machine.
- iOS Low Power Mode blocks video autoplay — the hero shows its poster instead.
- Each attached item of every work gets its own tiny `/w/` page, so a work with 30 images adds 30 small files; they're regenerated and cleaned up automatically.
